The 5 steps (28 min)

  1. Requirements 3 min · What it must do, how many users at once, and what must never go wrong (double booking, a wrong “free”).
  2. Estimates 4 min · Peak req/s, RAM or storage, servers. Measure one server with a load test (k6).
  3. HLD 8 min · Draw one request end to end: CDN · LB · gateway · services · cache · DB · queue.
  4. Deep dive 8 min · The hard part: seat lock + TTL, the existence filter, core count + cache, LB + network.
  5. Trade-offs 5 min · SPOF, C vs A per feature, cost (reads vs storage), sync and rebuilds, day one vs scale.

CAP in one line each

Consistencysame correct data everywhere → balances, seats, money
Availabilityalways answers, maybe stale → likes, views, cached lists
Partition tol.keeps working across nodes when the network splits; then choose C or A

Say it like this

  • “Seats and money need consistency; on a split I refuse rather than double-book. Likes can be available and a bit stale.”
  • “I squeeze one box first (PM2 workers, a short cache), then scale out behind a load balancer.”
  • “Slower after adding a server? I check the network first.”
  • “A Seat Lock in Redis with a TTL holds the seat and frees itself if they don’t pay.”
  • “The filter’s NO is a promise, its YES is a rumour, so I confirm every YES in the DB.”
  • “It cuts read cost, not storage: the DB is still the source of truth.”
  • “Not on day one. I’d add it when the stats show the DB hurting.”

🚩 Red flags

  • One server or one DB for everything; scaling with no load test.
  • pm2 -i max on a shared box; servers linked over Wi-Fi.
  • A seat lock with no TTL, or no lock at all.
  • Availability for balances or payments.
  • Email and SMS inside the checkout request (use a queue).
  • Saying “taken” because the filter said maybe.
  • Deleting from a Bloom filter; Fuse for data that keeps changing.
  • Forgetting RAM × workers, sync across servers, and sharding at 300 Cr.
  • Trusting file extensions, or an AI answer, without checking.
