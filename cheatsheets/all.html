The 5 steps (28 min)

  1. Requirements 3 min · What it must do, how many users at once, and what must never go wrong (double booking, a wrong “free”).
  2. Estimates 4 min · Peak req/s, RAM or storage, servers. Measure one server with a load test (k6).
  3. HLD 8 min · Draw one request end to end: CDN · LB · gateway · services · cache · DB · queue.
  4. Deep dive 8 min · The hard part: seat lock + TTL, the existence filter, core count + cache, LB + network.
  5. Trade-offs 5 min · SPOF, C vs A per feature, cost (reads vs storage), sync and rebuilds, day one vs scale.

Say it like this

  • “Seats and money need consistency; on a split I refuse rather than double-book. Likes can be available and a bit stale.”
  • “I squeeze one box first (PM2, a short cache), then scale out behind an LB. Slower after? I check the network.”
  • “Nginx sits in front: one public port, HTTPS and gzip at the edge; the app port stays private.”
  • “Likes go to Kafka and return 202; a consumer writes in batches and counts come from Redis.”
  • “A Seat Lock in Redis with a TTL holds the seat and frees itself if they don’t pay.”
  • “The filter’s NO is a promise, its YES is a rumour, so I confirm every YES in the DB. It cuts read cost, not storage.”
  • “Not on day one. I’d add it when the stats show the DB hurting.”

🚩 Red flags

  • One server or one DB for everything; scaling with no load test.
  • pm2 -i max on a shared box; servers linked over Wi-Fi.
  • Plain node in production; a k6 number without reading the script.
  • No TTL on a seat lock; availability for money.
  • Email and SMS inside the checkout request (use a queue).
  • One DB write per like; HyperLogLog for likes (it can’t subtract).
  • Saying “taken” because the filter said maybe.
  • Deleting from a Bloom filter; Fuse for data that keeps changing.
  • At 300 Cr: forgetting RAM × workers, sync, sharding.
  • Trusting file extensions, or an AI answer, without checking.

Guardrails · EP-6 · ▶ 22:34 · 29:11 · 30:42

AI only generates; it never touches the DB. Missed searches: no auto-add; the AI suggests a match, the admin approves with one click (one wrong tag spoils every search). Bad words are checked at 5 places (suggest, admin tags, Kafka worker, missed searches, trending); fail closed if Ollama is down; a veg product never gets a non-veg word.

Say it like this · EP-6

  • “I generate multilingual tags once, when the product is added, so the model is off the shopper’s path.”
  • “Tags catch exact words and typos; vectors catch meaning. Typesense ranks both together.”
  • “Saving a product returns 202; a Kafka worker tags, embeds and writes Mongo, Typesense and Redis.”
  • “Every search carries the dark store id, so results are only what that store can deliver.”

🚩 Red flags · EP-6

  • A wildcard LIKE on the DB as “search”.
  • Calling the LLM on every keystroke or search.
  • Auto-adding zero-result queries as tags.
  • Letting the model write to the DB.
  • One India-wide index for a 10-minute delivery app.
  • Elasticsearch on day one “because everyone uses it”.
