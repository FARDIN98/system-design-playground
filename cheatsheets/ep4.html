The 5 steps, for this episode

  1. Requirements 3 min · “Does X exist?” (username, UPI ID, blocked IP) at 300 crore, in ms, without a DB hit each time. A wrong “free” is not OK. Deletes?
  2. Estimates 4 min · bits/item ≈ 1.44 · log₂(1/p) (general). Bloom at 0.01% ≈ 2.4 B/record → 7.2 GB at 300 Cr, × workers.
  3. HLD 8 min · LB → servers, each with the filter in RAM. NO → 404. MAYBE → DB/ES → 200 or 404.
  4. Deep dive 8 min · Pick the filter (table). Sync: bulk-load + Redis Streams. Persist it for fast restarts.
  5. Trade-offs 5 min · Saves reads, not storage. RAM per worker. Rebuild time. Sharding. Not on day one.

The golden rule · ▶ 28:46

The filter’s NO is a promise, its YES is a rumour. Bits are shared by many items, so a 0 can only mean “never added”: no false negatives, only false positives. The false-positive rate is tunable: more bits or hashes, more RAM.

Say it like this

  • “A NO returns 404 straight away with no DB hit; a YES is only a maybe, so I confirm it in the DB.”
  • “It cuts read cost, not storage. Mongo stays the source of truth, so the disk bill stays.”
  • “Bloom can’t delete. If accounts can be deleted I’d take Cuckoo, which also shares one mmap file across workers.”
  • “I’d bulk-load the filter on startup and push every change to all servers with Redis Streams.”
  • “I wouldn’t add this on day one. I’d add it when the stats show DB reads hurting.”

🚩 Red flags: don’t say or do

  • Telling the user “taken” just because the filter said maybe.
  • Clearing Bloom bits to delete a name (other names vanish: false negatives).
  • Forgetting each worker holds its own copy (RAM × workers).
  • Binary Fuse for data that changes all the time.
  • Claiming the filter shrinks the storage bill.
  • One machine at 300 crore (you need sharding).
  • No plan to keep filters in sync across servers.
  • Repeating an AI claim unchecked: Chrome Safe Browsing uses a hash-prefix filter, not Binary Fuse (▶ 23:36).
