The 5 steps, for this episode

  1. Requirements 3 min · More load than one machine; no single point of failure; know where the bottleneck is.
  2. Estimates 4 min · Baseline one server first. req/s = requests ÷ seconds link cap ≈ speed ÷ reply size
  3. HLD 8 min · Users → Nginx LB → N app servers (PM2 × cores) → DB, on a wired switch; Prometheus + Grafana.
  4. Deep dive 8 min · Algorithms (round robin, least_conn, ip_hash…). Network between machines. Where k6 runs.
  5. Trade-offs 5 min · Reliability vs cost. Round robin vs least_conn. Wi-Fi vs cable. Sticky sessions vs even load (general).

Load balancers · ▶ 16:34

Software: Nginx (free, safe choice), HAProxy, Traefik, Envoy (microservices), Caddy (auto SSL), LVS. Cloud: AWS ALB/NLB, GCP, Azure, Cloudflare. Hardware: F5 BIG-IP, Citrix.

Say it like this

  • “One server is a single point of failure, so I run at least two behind a load balancer and keep each one lightly loaded.”
  • “Before scaling out, I load-test one server for a baseline, then rerun the same test after every change.”
  • “If throughput drops when I add servers, I check the network between them first: on Wi-Fi it fell 20×.”
  • “Round robin is fine for equal servers and short requests; with uneven requests I use least connections.”

🚩 Red flags: don’t say or do

  • Load-testing servers over Wi-Fi.
  • Running k6, Nginx and the DB on the server you’re measuring.
  • Blaming Nginx or the CPU without checking the network numbers.
  • Round robin with servers of very different speed.
  • “Just add machines”, with no word on cost and upkeep.
  • One big server with no backup (single point of failure).
