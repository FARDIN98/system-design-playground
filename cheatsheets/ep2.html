The 5 steps, for this episode

  1. Requirements 3 min · Product list API for a big sale. Know how far one server goes before buying more.
  2. Estimates 4 min · Load-test one server (k6, 0 → 3000 users, 2 min). MB/s ≈ req/s × KB ÷ 1000. Cores × ~2.3, not × 4.
  3. HLD 8 min · Users → Nginx (cache 15 s) → PM2 × N Fastify workers → MongoDB; Grafana watching.
  4. Deep dive 8 min · Node’s one core vs Go’s runtime. Picking the core count. proxy_cache_valid, HIT/MISS.
  5. Trade-offs 5 min · Cache = availability vs consistency (no balances). Compression = bytes vs CPU. One box = a ceiling.

CPU busy vs system load · ▶ 17:58

CPU busy = how hard the cashier works now. System load = how long the line is (over 100% = work waiting). He saw 47% busy with load 59% → 123%, and ~650% load on 10 workers.

Between tests: pm2 stop all · pm2 delete all, then let it cool down.

Say it like this

  • “Node is single-threaded, so one process uses one core. I run PM2 in cluster mode and measure the worker count, not -i max.”
  • “Before adding machines I squeeze one: a faster framework, the right core count, and a short Nginx cache.”
  • “I cache what can be a few seconds stale, like product lists; never a balance.”
  • “Compression saves bandwidth but costs CPU; I’d measure it, and Cloudflare only saves the customer-side hop.”

🚩 Red flags: don’t say or do

  • “Node can’t do backends.” One Node core can’t; scaled Node can.
  • pm2 start -i max on a box that also runs the DB and tools.
  • Back-to-back load tests without a cool-down.
  • Caching balances or anything that must be exact.
  • “Caching means Redis.”
  • Turning on compression without checking CPU.
  • Forgetting the limit: one box is a ceiling and a single point of failure.
