Duplicates and unlikes · ▶ 38:13 · 42:20

Kafka is at-least-once: an event can arrive twice. Unique index rejects the second like; Redis +1 only for rows really inserted. Unlike: deleteOne, then −1 only if deletedCount = 1, so a repeat never goes negative. Crash between Mongo and Redis = drift → reconcile job.

Say it like this

  • “The like API only puts the event in Kafka and returns 202; a consumer writes in batches, so a viral post can’t choke the DB.”
  • “Counts come from Redis counters, read in one pipelined call with the posts; I never count rows on page load.”
  • “Unique views go in a HyperLogLog: about 12 KB per post with a small error. Likes stay exact because they can be undone.”
  • “I change a counter only when the DB really changed, because Kafka can deliver twice.”

🚩 Red flags: don’t say or do

  • One DB write (or a count query) per like at scale.
  • HyperLogLog for likes: it can’t subtract.
  • −1 on every unlike event, with no deletedCount check.
  • Bloom for “liked”: unlike needs delete.
  • Five Redis round trips per event instead of one Lua call.
  • Installing whatever package the AI suggests without checking it.
