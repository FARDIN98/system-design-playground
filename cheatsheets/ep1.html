HLD vs LLD · ▶ 16:53

HLD = the big boxes and choices (DB, services, cache, queue, LB). LLD = the details inside (schema, APIs, error handling, refunds). Architect plans, engineer builds, customer only feels speed.

Scale up vs scale out · ▶ 30:14

Say it like this

  • “Seats and payments need consistency: on a network split I’d rather refuse than double-book. Likes can stay available and a bit stale.”
  • “I’d scale out, not up. One big server is a single point of failure; behind a load balancer one box can die and the rest keep serving.”
  • “A Seat Lock in Redis with a TTL holds the seat, and the TTL frees it by itself if they don’t pay.”
  • “For slow reads: index first, then read replicas, then sharding, in that order.”
  • “Checkout only accepts the order; email, SMS and stock updates go on Kafka in the background.”

🚩 Red flags: don’t say or do

  • One big server, or one DB, for everything.
  • Booking a seat with no lock, or a lock with no TTL (seats stuck forever).
  • Choosing availability for balances or payments.
  • Sending email and SMS inside the checkout request.
  • Product text search on Postgres (use Elasticsearch: fast text search, “did you mean”).
  • Trusting the file extension on uploads: check the signature (first bytes).
  • Scaling blindly with no load test (k6, Autocannon) or stress test.
  • No backups, or years of old rows in the main DB (archive them).
